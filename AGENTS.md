# Working on Workspaces

Instructions for an agent changing this package. `RECIPE.md` is what it is and
how it behaves; this file is how to change it without breaking what others
rely on. Read Herdr's own guide, `~/.config/herdr-app/AGENTS.md`, before
touching a mod or the layout.

## Where things live

- **The live files** are in your Herdr home, `~/.config/herdr-app/` (`layouts/workspaces.json`, `mods/ws-*`). Herdr reloads them within a second. Edit those.
- **This repo** is the package for sharing: `RECIPE.md`, `README.md`, `CHANGELOG.md`, the picture, the scripts, and copies of the live files that `scripts/sync-from-home.sh` makes. Don't edit the copies under `layouts/` and `mods/` here; edit the live ones and sync.
- **A person's own data** lives in `~/.herdr/` (workspaces, tasks, automations, presets, runner state). It's personal: never copy any of it into this repo.

## Each change

1. Edit the live files. Run `herdr-app check ~/.config/herdr-app/mods/<mod>` for each changed mod; `herdr-app status` must show no errors. Try it in the sandbox (below).
2. Update `RECIPE.md` in the same change: always How it behaves, Watch out and Done when; What you see when the look changes; Built from when the pieces change. Update the README's "What it touches" when a mod reads, writes or runs something new, or reaches the network.
3. Add a line under `## [Unreleased]` in `CHANGELOG.md` for anything a person would notice, in Herdr's format: `### New` or `### Fixed`, then `- **Headline.** detail`. Say what an existing install must do by hand (copy a new mod folder, link a new script). A new mod also changes the README's count of folders to copy.
4. Redraw the picture when the look it shows changes (below).
5. Run `scripts/sync-from-home.sh`. A new mod first needs adding to the list in that script, and a file copied between mods to its checks.
6. Check the package for personal paths and names (`/Users/`, `/home/`, real workspace or client names, emails) before committing.
7. Commit, push and release only when the person asks.

## The picture

`preview.png` (in the README and RECIPE) is rendered from the drawing `mods/ws-switcher/preview.svg`, which is also the picture Herdr's layout settings show. It's a drawing with demo names, never a screenshot: a screenshot would show someone's real workspaces, folders and agents. The same goes for the pictures in `previews/`.

- **Redraw it** when anything it shows changes: the sidebar (switcher, spaces, agents, footer rows), the switcher menu (its rows, their order and icons), the tab bar (view pills, tabs, +, Views), a pane's header or the status bar. Check it against RECIPE's What you see after each such change.
- **Every drawing, not only this one.** The sidebar, the tab bar's right end (+, Views, the bell) and the status bar are in every screen's drawing (below). A change to them (a new footer row, a new button by Views, a dot or count that comes or goes) is copied into all of them in the same change, then every picture is rendered again. `scripts/check-drawings.sh` compares the shared parts (sidebar, the switcher, spaces, footer) with this drawing's and looks for the bell in each; `render-preview.sh` and `release.sh` run it and stop when a drawing disagrees. Each part sits under its own comment (`<!-- footer -->` …): keep those comments when redrawing. A part the check doesn't cover yet, because a screen really draws it differently (the right-click drawing highlights an agent row), still has to change everywhere: look at each picture.
- **Edit the live drawing** (`~/.config/herdr-app/mods/ws-switcher/preview.svg`), sync, then run `scripts/render-preview.sh` and look at `preview.png`. `release.sh` refuses a release where a drawing changed and its picture didn't.
- **Icons** are the mods' own SVGs inlined (`<g transform="translate(x y) scale(0.583)">` with their paths for 14px), so the drawing stands alone.
- **Demo names**: workspaces Acme (blue `#5b8def`), Globex (orange `#e3814f`), Initech (green `#3fae6a`); spaces and folders `api`, `web`, `docs`, `infra`, `design-system`; paths under `~/work/acme/`. Reuse them in any new picture so they agree.
- **Each screen has its own drawing** beside its mod, rendered into `previews/` by the same script: `mods/ws-board/preview.svg` (the task board, `previews/board.png`), `mods/ws-board/preview-github.svg` (its GitHub view, `previews/github.png`), `mods/ws-worktrees/preview.svg` (`previews/worktrees.png`), `mods/ws-history/preview.svg` (`previews/history.png`), `mods/ws-notes/preview.svg` (`previews/notes.png`), `mods/ws-automations/preview.svg` (`previews/automations.png`), `mods/ws-agents/preview.svg` (the Agents list's right-click menu, `previews/agent-menu.png`) `mods/ws-settings/preview.svg` (the Settings window on Agents, `previews/settings.png`) `mods/ws-tabs/preview.svg` (the Views menu open, with Changes beside an agent, `previews/views.png`), `mods/ws-notifications/preview.svg` (the bell's list open, `previews/notifications.png`) and `mods/ws-vault/preview.svg` (Secrets open on a Protected secret, `previews/vault.png`). They share the first drawing's sidebar, tab bar (+ and Views at its right end), colors and demo data (cards ACM-1 to ACM-8, GitHub items #200 to #211, pull requests #12, #27 and #31), so a card shown in one agrees with the others. Redraw one when its screen's look changes, and check it against RECIPE's What you see.
- **A new screen** worth showing gets a drawing beside its mod, a line in the lists in `render-preview.sh` and `release.sh`, and a section with its picture in the README's "What you get".

## Shared across mods

A mod can't import from another mod's folder, so some things are copied. Change every copy together.

- **Copied files**, checked by the sync script, which refuses when copies differ: `when.js`, `knobs.js`, `check.js` and `autofacts.js` (an automation file's front matter and policies) in `ws-switcher` and `ws-automations`, and `knobs.js` also in `ws-presets` and `ws-agents`; `treescripts.js` in `ws-worktrees` and `ws-board`; `ghfacts.js` in `ws-switcher` and `ws-board`; `hidefacts.js` in `ws-new-menu` and `ws-settings`; `settingsfacts.js` in `ws-settings`, `ws-agents`, `ws-switcher`, `ws-status`, `ws-files`, `ws-automations` and `ws-vault`; `vaultfacts.js` in `ws-switcher` and `ws-vault` (a secret's rules: herdr-ws-secret and the Secrets screen); `vault.svg` in `ws-chrome`, `ws-settings` and `ws-vault` (the key on the sidebar row, Settings > Secrets and the screen); `menufacts.js` in `ws-agents` and `ws-history` (History's Wipe takes the same files; `TRASH` in their `main.js` is copied too, unchecked); `follow.js` in `ws-changes` and `ws-files`; `notif.js` in `ws-switcher` and `ws-notifications` (the bell's rules: the switcher keeps the log and the count, ws-notifications draws the list); `automations.svg` in `ws-automations` and `ws-settings` (Settings > Automations' icon). Not checked by the script: `EDITOR_CATALOG` in `ws-settings/settingsfacts.js` is a copy of the one in `ws-files/filesfacts.js` (Settings > Files lists the same editor ids Open in knows); change both.
- **Mod commands**: Herdr hands `<mod>.<anything>` to that mod's shown copies' `nextCommand()`, so a toast's `action` or a key can reach the switcher's sidebar copy (`ws-switcher.scratch-new`, `ws-switcher.scratch-keep/<folder>`, `ws-switcher.automation/<workspace>/<name>`). Check anything taken from the command text before using it in a path. Herdr refuses a mod's command while none of its copies is shown (a hidden sidebar unloads the switcher), so a toast action that must still do something from a desktop notification carries an `or`: the command `herdr-ws-notify --or` runs when the first is refused. That's also why the keys for Views are the tab bar's (`ws-tabs.view/<view>`, `ws-tabs.beside/<view>`), which ask the switcher through shared state.
- **Avatar colors**: the `MARK` table (`ansi1`…`ansi6` to one hex color each) is the same in every mod that draws a workspace or space mark (`ws-switcher`, `ws-spaces`, `ws-board`, `ws-worktrees`, `ws-history`, `ws-notes`, and `ws-notifications`' `notif.js`) and in the drawing.
- **The footer's row height**: `ROW` (28) in `ws-chrome/footer.js` must match the height `ws-chrome/main.js` draws a footer row at (`h(28)`); the footer's height with every row shown is `sidebar-footer`'s px in `layouts/workspaces.json`, which ws-chrome reads.
- **Shared state**: mods talk through Herdr's shared keys `workspaces.*`. The list and what each holds is at the top of `mods/ws-switcher/main.js`; add a new key there. A screen or popup asks the sidebar copy of the switcher to do work by setting a key to `{ …, at: Date.now() }`, because a popup's or dialog's tasks end when it closes.
- **Config formats**: a workspace is `~/.herdr/workspaces/<id>/workspace.jsonc` plus `AGENTS.md`; presets are herdr-core templates (front matter `description` and `command`, the body is the instructions); automations and tasks are markdown with front matter. Build on these instead of inventing new files. `defs.js` loads workspaces and presets for both the app and the background runner.
- **The background runner** runs `automations.js` (with what it imports, `runfacts.js` among them), `prs.js`, `ghboard.js` and `defs.js` under Node with stand-ins for the `herdr` module (`runner/herdr.js`). Code in those files may only use what the stand-ins provide.
- **Copies of Herdr's own mods** (`ws-spaces`, `ws-agents`, `ws-tabs`, `ws-new-menu`, `ws-chrome`, `ws-toast`, `ws-status`, and `ws-changes` and `ws-files`, from Herdr 0.1.17's `changes` and `files`) are based on a stated Herdr version. Note every change at the top of the copy and in RECIPE's Built from, so they can be rebuilt on a newer Herdr.
- **`ws-settings/main.js` is generated**: the switcher (`settingsbuild.js`) writes it from Herdr's own `frame/settings/main.js` with a few anchored patches, whenever Herdr's file changes and each time the switcher starts (so a new `settingsbuild.js` is picked up as soon as it's copied in). Never edit it; change `settingsbuild.js` (or `ws-settings/extras.js` for the Features, Agents and Experimental pages), and when Herdr's Settings changes so that a patch's anchor is gone (the copy is then the fallback, our sections alone), update the anchor there.

## Testing

- **The sandbox**: `scripts/sandbox.sh up` is a second Herdr with its own core, home and demo workspaces (Acme, Blog) under `/tmp/herdr-ws-sandbox`, running copies of the live mods; `sync`, `app …`, `hc …` and `down`. Use it for screens and anything that opens a dialog. Its window does appear on the screen: say so before opening it, and take it `down` after.
- **Reading state**: `herdr-app status` (shown space, overlays, errors), `herdr-app shot file.png` (the last rendered frame), and `shared.json` in the Herdr home for what mods published. In the sandbox, `sandbox.sh app status` and its own `shared.json`.
- **Driving it**: `herdr-app do <command> '<json>'` (`herdr-app commands` lists them; `space.close` needs `"confirmed": true`). A stand-in agent is a script that prints `ESC ] 7501 ; state=working:app=x ESC \` (then `state=done`).
- **Unit checks**: `ws-switcher/autofacts.js` (an automation file's front matter, `check: |` blocks included, its timeout, notify, missed and dedupe rules, chaining loops, quiet hours and how many runs are kept), `ws-automations/drafter.js` (the drafter's CLI commands for claude, codex, agy and pi, and reading each one's answer), `facts.js` (worktrees), `prfacts.js` (pull requests), `ws-switcher/runfacts.js` (when a finished automation run's tab closes), `ghfacts.js` (GitHub boards), `histfacts.js` (History), `ws-history/treefacts.js` (History's tree: `hc run` calls read out of a transcript and matched to their helpers, the ledger, the folding and search, the right-click menu, what stands in the way of a wipe), `ws-notes/notesfacts.js` and `ws-notes/notestate.js` (Notes; the second with a fake disk), `ws-board/startfacts.js` (the board's Start with…), `ws-agents/statfacts.js` (the Agents list's numbers, and whether an Antigravity note is its running process's), `ws-agents/menufacts.js` (its right-click menu), `ws-agents/pbfacts.js` (the Antigravity wipe's edits: the summary file's protobuf wire format, the cache JSON and prompt history edited as text, a conversation's tree, the `ps` listings and which processes are Antigravity's, the backup's pass folders, the pending list's next step), `ws-settings/settingsfacts.js` (the package's settings file, Files' defaults in it included), `ws-new-menu/hidefacts.js` (which agents the + menu shows), `ws-status/usagefacts.js` (the status bar's plan usage), `ws-switcher/knobs.js` (each agent's model and effort flags, its model list parsers, the agent switch in a command and the model box's rows: `typeahead`, `markSegments`), `ws-switcher/arrange.js` (the menu's groups and order), `ws-switcher/settingsbuild.js` (ws-settings' main.js from Herdr's Settings: test it against the real `frame/settings/main.js` and with an anchor removed), `ws-switcher/featuregate.js` (Settings > Features in the switcher and the background runner: the file's answer first, then shared flips, and when an `every` automation runs after Automations comes back), `ws-chrome/footer.js` (the sidebar footer's rows, Secrets' among them, and height), `ws-settings/brokerfacts.js` (Settings > Secrets' broker row for each `herdr-ws-secret broker status` answer), `ws-vault/vaultview.js` (the Secrets screen: its states, rows, a secret's form, what Save sends and whether macOS will ask; it imports `vaultfacts.js`, which is pure too), `ws-switcher/vaultfacts.js` (a secret's names, scopes, hosts, commands, expiry, redaction and redirects), `ws-tabs/views.js` (the Views menu's rows for each state, the pills' order, when pills go icon-only, key labels, the ask list `pushAsk`), `ws-switcher/beside.js` (a view opened beside the terminals: where its pane opens, which to close, when a ledger entry is forgotten; `drainAsks`, each of the tab bar's asks done once, in order), `ws-changes/follow.js` (which terminal, folder and machine Changes and Files follow, and who writes that memory), `ws-changes/repos.js` (Changes' nested repo discovery, worktree list parsing, deduplication by common dir, alphabetical grouping, initial checkout selection and filtering), `ws-notifications/notif.js` (the bell: which toasts are kept, the list built from live state and the log, read, dismissed and their expiry, the count, the list's height, a run's outcome off its screen) and `ws-files/filesfacts.js` (Files: a file's kind and language, which Cmd-clicked paths it takes, link and path parsing, the tree filter, search output, an SVG's size and an image's box, the Open in … list, its default and memory, launch commands, the `workspaces.files.open` ask list and whose target it is) have no imports, so `node` can test them directly.
- **Quirks**: an edited mod may only reload on the next draw, so the first click after an edit can run the old code. `mod.open` shows a dialog only about 500px wide, unless the mod's `mod.json` gives its `overlay` a width (as `ws-settings`' does). A mod's `fs` only reads under home. A window behind others doesn't redraw, so wait and check `status` before trusting a `shot`.
- **Never stop processes by a name pattern** (`pkill -f`): a person's agents and the background runner match more than you expect. Stop what you started, by its id.

## Releases

`CHANGELOG.md` is what people read to update; `VERSION` (copied into `mods/ws-switcher/VERSION`) says which version a copy is. The middle number is for anything new, the last for fixes only.

- `scripts/release.sh <version>` turns `## [Unreleased]` into that version, writes `VERSION`, commits and tags. `--publish` pushes and makes the GitHub release from those notes; people watching the repo's releases are notified.
- After a release, copy `VERSION` to the live `~/.config/herdr-app/mods/ws-switcher/VERSION`. `release.sh` only writes this repo's copies, and the sync goes the other way (it takes this repo's `VERSION`), so the live copy says which version is installed only if you set it.
- A release is one coherent thing. When unrelated work is pending (another feature half-done), release the finished part alone and leave the rest under Unreleased.
