# Working on Workspaces

Instructions for an agent changing this package. `RECIPE.md` is what it is and
how it behaves; this file is how to change it without breaking what others
rely on. Read Herdr's own guide, `~/.config/herdr-app/AGENTS.md`, before
touching a mod or the layout.

## Where things live

- **The live files** are in your Herdr home, `~/.config/herdr-app/` (`layouts/workspaces.json`, `mods/ws-*`). Herdr reloads them within a second. Edit those.
- **This repo** is the package for sharing: `RECIPE.md`, `README.md`, `CHANGELOG.md`, the picture, the scripts, and copies of the live files that `scripts/sync-from-home.sh` makes. Don't edit the copies under `layouts/` and `mods/` here; edit the live ones and sync.
- **A person's own data** lives in `~/.herdr/` (workspaces, tasks, automations, presets, runner state). It's personal: never copy any of it into this repo.

## Each change

1. Edit the live files. Run `herdr-app check ~/.config/herdr-app/mods/<mod>` for each changed mod; `herdr-app status` must show no errors. Try it in the sandbox (below).
2. Update `RECIPE.md` in the same change: always How it behaves, Watch out and Done when; What you see when the look changes; Built from when the pieces change. Update the README's "What it touches" when a mod reads, writes or runs something new, or reaches the network.
3. Add a line under `## [Unreleased]` in `CHANGELOG.md` for anything a person would notice, in Herdr's format: `### New` or `### Fixed`, then `- **Headline.** detail`. Say what an existing install must do by hand (copy a new mod folder, link a new script). A new mod also changes the README's count of folders to copy.
4. Redraw the picture when the look it shows changes (below).
5. Run `scripts/sync-from-home.sh`. A new mod first needs adding to the list in that script, and a file copied between mods to its checks.
6. Keep the installers (`install.sh`, and `install.ps1` for Windows) doing what the README's Install by hand says. They copy every `mods/ws-*` folder, so a new mod needs nothing there. A new command in `ws-switcher/bin` is added to `commands` in `install.sh` (on Windows the whole folder is on `Path`), and a new step of Install by hand to both scripts.
7. Check the package for personal paths and names (`/Users/`, `/home/`, real workspace or client names, emails) before committing.
8. Commit, push and release only when the person asks.

## Shared across mods

A mod can't import from another mod's folder, so some things are copied. Change every copy together.

- **Copied files**, checked by the sync script, which refuses when copies differ: `when.js`, `knobs.js`, `check.js` and `autofacts.js` (an automation file's front matter and policies) in `ws-switcher` and `ws-automations`, and `knobs.js` also in `ws-presets` and `ws-agents`; `treescripts.js` in `ws-worktrees` and `ws-board`; `ghfacts.js` in `ws-switcher` and `ws-board`; `hidefacts.js` in `ws-new-menu` and `ws-settings`; `settingsfacts.js` in `ws-settings`, `ws-agents`, `ws-switcher`, `ws-status`, `ws-files`, `ws-automations` and `ws-vault`; `vaultfacts.js` in `ws-switcher` and `ws-vault` (a secret's rules: herdr-ws-secret and the Secrets screen); `vault.svg` in `ws-chrome`, `ws-settings` and `ws-vault` (the key on the sidebar row, Settings > Secrets and the screen); `copy.svg` in `ws-vault` and `ws-settings` (Copy example and Copy the shell line); `menufacts.js` in `ws-agents` and `ws-history` (History's Wipe takes the same files; `TRASH` in their `main.js` is copied too, unchecked; so is `ws-files/main.js`' `TRASH` in `ws-changes/main.js`, for Changes' Discard changes…); `follow.js` in `ws-changes` and `ws-files`; `gitscan.js` in `ws-changes` and `ws-files` (the one `git status` per repo they share, and its brake); `notif.js` in `ws-switcher` and `ws-notifications` (the bell's rules: the switcher keeps the log and the count, ws-notifications draws the list); `automations.svg` in `ws-automations` and `ws-settings` (Settings > Automations' icon). Not checked by the script: `EDITOR_CATALOG` in `ws-settings/settingsfacts.js` is a copy of the one in `ws-files/filesfacts.js` (Settings > Files lists the same editor ids Open in knows); change both.
- **Mod commands**: Herdr hands `<mod>.<anything>` to that mod's shown copies' `nextCommand()`, so a toast's `action` or a key can reach the switcher's sidebar copy (`ws-switcher.scratch-new`, `ws-switcher.scratch-keep/<folder>`, `ws-switcher.automation/<workspace>/<name>`). Check anything taken from the command text before using it in a path. Herdr refuses a mod's command while none of its copies is shown. A sidebar hidden since Herdr started never loads the switcher; one hidden later leaves it running, but its commands are refused all the same. So a toast action that must still do something from a desktop notification carries an `or`: the command `herdr-ws-notify --or` runs when the first is refused. That's also why the keys for Views are the tab bar's (`ws-tabs.view/<view>`, `ws-tabs.beside/<view>`), which ask the switcher through shared state. The command palette's entries are the tab bar's too (`ws-tabs.*` in its `mod.json`), for the same reason: the bar answers with a toast when an add-on is off or the switcher isn't running.
- **Is the switcher there?** It writes `workspaces.switcher.alive` (`{ at }`) when it starts and every 5 seconds. A screen or a popup that asks the switcher to do something reads it first: missing or older than 15 seconds, it says "Show the sidebar to do this" in place (`muted`) and posts no ask, since nobody would answer. A popup's row never awaits what it starts (the row closes the popup first, and the popup's tasks end with it): it sets the key and the sidebar copy does the steps.
- **Avatar colors**: the `MARK` table (`ansi1`…`ansi6` to one hex color each) is the same in every mod that draws a workspace or space mark (`ws-switcher`, `ws-spaces`, `ws-board`, `ws-worktrees`, `ws-history`, `ws-notes`, and `ws-notifications`' `notif.js`) and in the drawing.
- **The footer's row height**: `ROW` (28) in `ws-chrome/footer.js` must match the height `ws-chrome/main.js` draws a footer row at (`h(28)`); the footer's height with every row shown is `sidebar-footer`'s px in `layouts/workspaces.json`, which ws-chrome reads.
- **Shared state**: mods talk through Herdr's shared keys `workspaces.*`. The list and what each holds is at the top of `mods/ws-switcher/main.js`; add a new key there. A screen or popup asks the sidebar copy of the switcher to do work by setting a key to `{ …, at: Date.now() }`, because a popup's or dialog's tasks end when it closes.
- **Keys in a dialog or popup**: three keys never reach a mod's `on_key_down` there, so a rule written in it does nothing. Each was found by pressing real keys, which the sandbox can't do.
  - **Esc** arrives as Herdr's action `overlay.close`, and Cmd/Ctrl+W as `tab.close` or `pane.close`. A dialog whose Esc must ask first, wait while it saves, go back one level or empty a box claims them on its root, as Herdr's own Settings does: `.on_action("overlay.close", (_e, cx) => { cx.stop_propagation(); this.guardedClose(cx); })`, and the same for `"tab.close"` and `"pane.close"`. A handler that returns without closing keeps the dialog open. Claim it only while there is something to guard (`.when(…)`), and `tab.close`/`pane.close` only on a root that is drawn as a dialog or popup, or Cmd+W stops closing a tab. Something inside the root has to hold the keyboard: focus its handle or a box in `init`.
  - **Cmd/Ctrl+Enter in a box of several lines** is taken by the box: it adds a line break and emits `submit` with `secondary: true`. Listen there (`input.on("submit", (e, cx) => e.secondary && save(cx))`) and take the added break out again.
  - **A dialog that keeps what you typed** is opened with `modal: true` (a click beside it doesn't close it), has a Close × or a Cancel, and asks once before dropping changes: "Press Esc again to close and drop what you typed." or "Click × again…", in `working`; any other press or key takes the question back; while it saves or deletes, Esc, × and Cancel do nothing.
- **A press that can't be undone** (a delete, a discard, a forced remove, a run started) is guarded three ways, each found by a review or a real press:
  - **Ask in place, name the thing.** The first press turns the footer into Cancel and "Delete “name”" with what becomes of it; a press on that pair within 500 ms of the first doesn't count, so a double-click only asks. Cancel, any key, a click elsewhere, picking another item, Esc and the Close × take the question back, and while the question shows nothing else may ask behind it (an ask line the armed footer hides is never seen).
  - **A held key isn't a second press.** Key repeats reach `on_key_down`: where Enter confirms, test `!e.is_held`, or holding Enter walks through the question.
  - **A button that moves under the pointer waits.** When a press makes one button go and another slide into its place (Discard goes and Run now takes its spot; a deleted note's bar becomes the next note's; a strip goes and the one under it moves up), the newcomer ignores presses for 500 ms. Compare stamps as `d >= 0 && d < 500`, so a clock set back can't freeze the screen, above all for a stamp kept in shared state.
  - **Enter answers one thing.** A menu row runs on Enter's key up, on the row the key went down on: run on key down, a held Enter's repeats reach the dialog the row opened and answer it. A dialog that deletes also ignores an Enter in its first half second. And a box's own `submit` sees the same Enter as a menu or question drawn over it, in an order a mod can't rely on: `submit` returns while one is up, or was taken back by a key within 300 ms.
  - **A dialog that looks again by itself remembers what it drew.** When what a button acts on can change without a press (a timed re-check), compare at the press what was on screen with a fresh look, refuse and show the change when they differ, and don't count a press within 500 ms of a change. A failure that changed things itself gets one more look before its error shows, or the next timed look clears the error as a change.
  - **A step that deletes or overwrites a file asks the disk first, and fails closed.** A path from a row goes to git literally (`--literal-pathspecs`: `pages/[id].tsx` is a pattern otherwise). Before `git checkout HEAD -- path` or a move to the Trash, stop when a real folder is at the path, when a file or link sits at a name above it, or when another row is the same file on this disk (`-ef`, not the platform's rule for case). Go on only on the check's own go-on answer; a throw, a timeout or any other code stops. A folder that is a repository of its own is told by its gitlink in the index (mode 160000), not by a trailing slash.
  - **A rename is a write and a delete, and both can fail apart.** Check the old file is still what was opened, refuse a target that exists and isn't the same file (a caseless disk makes a case-only rename the same file; a case-sensitive one makes it another), and when the delete fails say both exist. What follows a name (a chain, earlier runs, an allowance, a secret's grant) is moved or named in the notice.
- **Menus, popups and the keyboard**, each found by a real press:
  - **The keyboard can't be handed back to a terminal.** A mod can take the keyboard for a menu it draws, but Herdr gives it no sure way to give it back to the terminal pane that had it (`pane.focus` on the pane Herdr still counts as focused moves nothing). So a menu in a view beside terminals leaves the keyboard where it is; a box of the mod's own can be focused again, and is, on every way its popup closes (its button, Esc, a pick, a press outside).
  - **One lit row.** In a menu with arrow keys, the lit row is the one Enter runs, and rows have no hover fill of their own. It follows the pointer only when the pointer moves: keep the last pointer position, start it from the press that opened the menu, and ignore a move at the same place (a menu that opens under a resting pointer keeps its first row, and a re-sent move never pulls the row back after the arrows moved it).
  - **A tooltip is off while what its button opened is up.** A tooltip on a button, or on a row with a right-click menu, otherwise sits on top of the menu, panel or dialog under it. Switch it off by that thing's own state (open or not) where there is one; a "gone until the pointer leaves" flag comes back after one typed letter, because a key press ends hover.
  - **A button closes its own popup.** A press on the button is a press outside the popup, which closes it, and the click that follows opens it again. Note when the popup closed and ignore the button's click within 300 ms of that; when two buttons open the same mod's popup, say in the mark which one did.
  - **A button whose label changes keeps its widest width from the start** (lay the other labels out unseen inside it), so the button beside it never moves and a red label never lands where Cancel was.
  - **A dialog opened by a menu that closes itself starts its work from its own timer.** Such a dialog runs its `init` inside the menu's call, and async work begun there (past its first plain `await`) belongs to the menu: once the menu has gone, Herdr drops the answer and the dialog waits for good. Start that work from the dialog's own `cx.timer.after(1, …)`, not in `init`.
  - **A box that goes away still holds the keyboard.** When an edit row or a popup with its own box closes, nothing drawn has the keyboard until a click. Give it back to where it came from on every way it closes, but only while the box still had it (its own focus and blur events): after an awaited step the person may have clicked into a terminal meanwhile.
  - **A filter never hides what the person just made**, and a fold or a tag never rests on a guess: empty a search when something added through the screen wouldn't match it, and hide or tag only by a record.
- **Copying on Linux**: `wl-copy` and `xclip` stay behind to serve the clipboard and keep the pipe an `exec` waits on, so the call only returns when something else takes the clipboard. Send their own output to `/dev/null`; the exit code still says whether it worked.
- **A copied shell line on Windows** runs in PowerShell 5.1: no `&&` there. Part two commands with `;` and quote with doubled single quotes.
- **What an automation may run**: a check or script becomes allowed only by Save, Create or Overwrite pressed as a plain save on the text the editor shows, or by Allow on the part its strip names. The allowance rides on `save()` in `ws-automations`, so every other caller says what it does: a switch or a quick fix keeps what was allowed, a rename or a copy carries its source's (a part only when its text is the one that was allowed), and a save the file refused remembers which it was for its Overwrite. Never allow text that isn't on screen at the press.
- **A screen that reads by itself stops when nobody can see it.** A timer that reads git or GitHub runs only for the layout's screen, while it is the one shown and `window()?.visible !== false`. A tab or pane copy can't tell whether it is in front: it reads when opened, on Refresh and after a change it caused.
- **A toast shows two lines of its body.** What a person must act on (a command, a path) goes first or into the toast's command row with Copy, never only at the end. `ws-toast` finds that command by the poster's words, so a change of words on one side needs the other, and a unit check holds the pair.
- **Showing an agent in another workspace** takes the switcher first: set `workspaces.active` to the workspace of the agent's space, then focus its pane, or nothing visible happens while the shown workspace is empty. To name something after its tab, test `tab.named` first: an unnamed tab's `name` is its number.
- **Something that can be missing says so from the start** (Node, a program on the PATH): look once when the mod starts, not at the first action that needs it.
- **Sizes from `on_size_change` are window pixels.** Divide by `settings().zoom` before comparing with a width written in the mod, or a limit is off by the zoom.
- **Config formats**: a workspace is `~/.herdr/workspaces/<id>/workspace.jsonc` plus `AGENTS.md`; presets are herdr-core templates (front matter `description` and `command`, the body is the instructions); automations and tasks are markdown with front matter. Build on these instead of inventing new files. `defs.js` loads workspaces and presets for both the app and the background runner.
- **The background runner** runs `automations.js` (with what it imports, `runfacts.js` among them), `prs.js`, `ghboard.js` and `defs.js` under Node with stand-ins for the `herdr` module (`runner/herdr.js`). Code in those files may only use what the stand-ins provide. The stand-in `watchFolder` is Node's `fs.watch` with `recursive`, which on Linux watches each file by its inode, so a file saved by rename is seen once and then not: what the runner must not miss it reads again (`fresh()` before a start, the minute's look in `runner/poll.js`).
- **Copies of Herdr's own mods** (`ws-spaces`, `ws-agents`, `ws-tabs`, `ws-new-menu`, `ws-chrome`, `ws-toast`, `ws-status`, and `ws-changes` and `ws-files`, from Herdr 0.1.17's `changes` and `files`) are based on a stated Herdr version. Note every change at the top of the copy and in RECIPE's Built from, so they can be rebuilt on a newer Herdr.
- **`ws-settings/main.js` is generated**: the switcher (`settingsbuild.js`) writes it from Herdr's own `frame/settings/main.js` with a few anchored patches, whenever Herdr's file changes and each time the switcher starts (so a new `settingsbuild.js` is picked up as soon as it's copied in). Never edit it; change `settingsbuild.js` (or `ws-settings/extras.js` for the Features, Agents and Experimental pages), and when Herdr's Settings changes so that a patch's anchor is gone (the copy is then the fallback, our sections alone), update the anchor there.

- **Quirks**: an edited mod may only reload on the next draw, so the first click after an edit can run the old code. `mod.open` shows a dialog only about 500px wide, unless the mod's `mod.json` gives its `overlay` a width (as `ws-settings`' does). A mod's `fs` only reads under home. A window behind others doesn't redraw, so wait and check `status` before trusting a `shot`. `herdr-app do` runs commands, not keys or clicks: what a key, a hover or a drag does has to be tried by hand, or with a tool that presses real keys (ydotool in a Linux VM did it for the dialogs).
- **Never stop processes by a name pattern** (`pkill -f`): a person's agents and the background runner match more than you expect. Stop what you started, by its id.

## Releases

`CHANGELOG.md` is what people read to update; `VERSION` (copied into `mods/ws-switcher/VERSION`) says which version a copy is. The middle number is for anything new, the last for fixes only.

- `scripts/release.sh <version>` turns `## [Unreleased]` into that version, writes `VERSION`, commits and tags. `--publish` pushes and makes the GitHub release from those notes; people watching the repo's releases are notified.
- After a release, copy `VERSION` to the live `~/.config/herdr-app/mods/ws-switcher/VERSION`. `release.sh` only writes this repo's copies, and the sync goes the other way (it takes this repo's `VERSION`), so the live copy says which version is installed only if you set it.
- A release is one coherent thing. When unrelated work is pending (another feature half-done), release the finished part alone and leave the rest under Unreleased.
